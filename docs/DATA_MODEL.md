# מודל הנתונים — המגרש PRO

גרסת סכמה נוכחית: **4**

כל הנתונים חיים על המכשיר של המורה. אין שרת, אין חשבון ואין סנכרון.
זה מה שנותן את הפרטיות — והמסמך הזה קיים כי בדיוק זה גם מה שהופך כל
טעות במודל הנתונים לאובדן שאין ממנו חזרה.

## איפה יושבים הנתונים

| אחסון | מה | למה שם |
|---|---|---|
| `localStorage`, תחילית `pehub.` | הכול חוץ מסרטונים | מהיר, סינכרוני, נוח לגיבוי כ-JSON |
| `IndexedDB` → `pehub-records` → `rec` | שיאי בית הספר, כולל הסרטון כ-`Blob` | `localStorage` לא מחזיק בינאריים ומוגבל ל-~5MB |
| `sessionStorage` | תפקיד המשתמש בטאב הנוכחי | מכוון: תלמיד שפתח טאב לא נשאר תלמיד לנצח |

**נקודה קריטית:** זה המקום היחיד באפליקציה שבו הנתונים פזורים בין שני
מנגנוני אחסון. כל דבר שנוגע ב«כל הנתונים» — גיבוי, שחזור, מחיקה —
חייב לגעת בשניהם. בגרסה 1 של קובץ הגיבוי זה לא קרה, וסרטוני השיאים
לא היו בפנים.

## שרשרת הזהות

```
Class  ──<  Student  ──<  Measurement  ──>  Assessment
 cid          sid            sid+cid          ציון נגזר
```

| ישות | הזהות | התצוגה | איפה |
|---|---|---|---|
| **Class** | `cid` | `name` | `ft.classes` |
| **Student** | `id` / `sid` | `name` | `stu.list` — מאגר אחד |
| **Measurement** | `id` | — | `ft.results` |
| **Assessment** | — | — | נגזר, לא נשמר |
| **Progress** | — | — | נגזר, לא נשמר |

**Test** נושא מזהה יציב משלו (`r60`, `push`, `ljump`) שאינו תלוי
בשם התצוגה, בתרגום או במיקום במערך. ‎30‎ מבחנים, כולם עם `dir`
מפורש — «נמוך יותר טוב יותר» או «גבוה יותר טוב יותר».

**Assessment אינו נשמר.** הציון מחושב מחדש בכל תצוגה מתוך המדידה,
טבלת הנורמה ומצב הניקוד. המודל המלא — כולל שיא אישי, כיוון מבחן,
התקדמות וגרסאות — ב-`docs/PROGRESS_MODEL.md`. זה מכוון: ציון שמור היה מתיישן ברגע שהמורה
מעדכן נורמה, ואז שני מסכים היו מציגים שני מספרים שונים לאותו תלמיד.
היוצא היחיד הוא מדד הכושר שנכתב לעמודת ציון — שם זו כתיבה מפורשת של
המורה לקובץ הציונים, לא מטמון.

## הטיפוסים

### `Class` — `ft.classes[cid]`

```js
{
  id:    "c:ט:3",     // חובה. לא משתנה לעולם.
  name:  "ט׳3",       // תצוגה בלבד. ניתן לשינוי.
  grade: "ט",         // null לכיתה שאינה נפרסת לשכבה+מספר
  num:   3,           // null באותו מקרה
  key:   "ט3"         // המפתח ב-ft.roster
}
```

**איך נגזר המזהה:**

| התווית | המזהה | למה |
|---|---|---|
| `ט׳3`, `ט3`, `ט' 3` | `c:ט:3` | נפרסת לשכבה+מספר — כולן אותה כיתה |
| `נבחרת בית ספר` | `cn:נבחרתביתספר` | טקסט חופשי — המפתח המנורמל |
| `""`, `null` | `null` | אין כיתה |

הגזירה מהתוכן היא מה שהופך את ההסבה לדטרמיניסטית: אותו מכשיר ייתן
תמיד את אותם מזהים, ואין צורך ב-`Date.now()`.

**אחרי שהכיתה רשומה, המזהה מנותק מהתווית.** שינוי שם דרך
`renameClass` נוגע ב-`ft.classes` בלבד; המדידות והתלמידים ממשיכים
להצביע על אותו `cid`. שתי כיתות רשאיות לשאת אותו שם ולהישאר שתיים.

### `Student` — `stu.list`

```js
{
  id:   "s" + <מזהה יציב>,   // חובה. לא משתנה לעולם.
  name: "דן אבירם",           // תצוגה בלבד. משתנה בכל תיקון שגיאת כתיב.
  cls:  "ט׳3",
  sex:  "boys" | "girls" | null,
  age:  14, h: null, w: null,
  cid:  "c:ט:3",              // הכיתה, כזהות. נגזר מ-cls.
  tests:  [...],              // מבחני ריצה שנרשמו בכרטיס התלמיד
  grades: {...}               // ציונים לפי תקופה
}
```

### רשימת הכיתה — `ft.roster[cid]`

```js
{ "c:ט:3": ["s-a1b2","s-c3d4"] }
```

**חברוּת בלבד.** עד סכמה 5 היא החזיקה רשומות מלאות (`{id,name,sex}`)
במקביל לאותם שדות ב-`stu.list` — שתי תשובות לאותה שאלה. זה לא היה
תיאורטי: כפתור «בן/בת» ברשימת הכיתה כתב לכאן, כרטיס התלמיד כתב
ל-`stu.list`, **והמין קובע נורמה** — כלומר אותו תלמיד יכול היה
להיות מנוקד לפי נורמת בנים במסך אחד ולפי נורמת בנות בשני.

מאז ‎4→5‎: `stu.list` הוא מאגר התלמידים היחיד, וכאן נשארים המזהים
והסדר. שלוש פונקציות ב-`hm-data.js` הן הנקודה האחת שבה מזהה הופך
לתלמיד ובחזרה — `rosterOf` (קריאה), `setRosterOf` (כתיבה),
`removeFromRosters` (מחיקת תלמיד). הקריאה מגוננת: מפתח שהוא תווית
ורשומה שהיא אובייקט עדיין נקראים, כי גיבוי ישן מגיע לפני שההסבה
הספיקה לרוץ.

### `Measurement` — `ft.results`

```js
{
  id:   "f…",            // מזהה הרשומה
  ts:   1757520000000,   // חותמת זמן

  cls:  "ט׳3",           // תצוגה

  sid:  "s…" | null,     // ← הזהות האמיתית

  sex:  "boys" | null,

  cidAmbig: "no-class",               // מדידה בלי שדה כיתה
```


## זהות תלמיד — הכלל

> **המזהה קובע. השם הוא תצוגה.**

```js
sameStudent(rec, stud):
  אם לשניהם יש מזהה  → התאמה רק אם המזהים זהים
  אם לרשומה אין מזהה → התאמה לפי שם     (רשומה ישנה)
  אחרת                → אין התאמה
```

הכלל האמצעי הוא מה שהופך את המעבר לבטוח. רשומה שההסבה לא הצליחה
לשייך נשארת נגישה בדיוק כמו קודם, לפי שם, במקום להיעלם.

**למה זה חשוב:** עד גרסה 2 כל חיפוש היסטוריה עבד על `r.name===name`.
מורה שתיקן שגיאת כתיב בשם ניתק בשקט את כל המדידות של התלמיד; שני
תלמידים בשם «דן כהן» חלקו היסטוריה אחת. שניהם באגים שקטים — אף
הודעה, אף סימן, והתגלו רק כשמישהו חיפש נתון שלא היה שם.

**המזהה ב-DOM.** גם השורות במסך מפתוחות לפי `refKey(student)`
(`"id:<sid>"` או `"nm:<שם>"` לתלמיד בלי מזהה) ולא לפי השם, אחרת שני
תלמידים זהי-שם היו נדרסים זה על זה בממשק גם כשהנתונים תקינים.

## גרסאות סכמה והסבה

ההסבה רצה פעם אחת ב-`HMBoot`, לפני שמודול כלשהו קרא נתון. מימוש:
`hm-data.js` → `migrate(store)`.

שלושה כללים שאסור להפר:

1. **דטרמיניסטי** — מזהים נגזרים מהתוכן (`FNV-1a` על `כיתה|שם`) ולא
   מ-`Date.now()`, ולכן שתי ריצות נפרדות מגיעות לאותה תוצאה בדיוק.
2. **`idempotent`** — ריצה שנייה לא משנה אף בית.
3. **לא הרסני** — אין מחיקה, אין ניחוש, ואף נתון לא יורד לטמיון.

עד ‎3→4‎ הכלל השלישי היה חזק יותר: **רק הוספת שדות.** ‎4→5‎ היא
הראשונה שמשנה מבנה — שורה ברשימת כיתה הופכת למזהה. «לא הרסני»
שם פירושו שכל שדה שהיה על השורה עובר ל-`stu.list` לפני שהשורה
מתכווצת, ושתלמיד שהיה רק ברשימה יוצא מההסבה עם כרטיס. מה שלא
ניתן להעביר בוודאות לא נגעו בו בכלל.

### 4 → 5 · `roster-membership`

| שלב | פעולה |
|---|---|
| א | מפתח הרשימה עובר מתווית (`"ט3"`) ל-`cid` (`"c:ט:3"`) |
| ב | כל שורה הופכת ל-`sid`; תלמיד שהיה רק ברשימה מקבל כרטיס ב-`stu.list` |
| ג | תווית ו-`cid` שמצביעים על אותה כיתה מתמזגים לרשימה אחת |

מפתח שאי אפשר לפתור לזהות אחת — שתי כיתות שנושאות אותו שם —
**נשאר כפי שהוא**, ונספר ב-`rosterKept`. שיוך שגוי כאן קובר תלמיד
בכיתה שהוא לא בה, בשקט.

מזהה על השורה הוא הזהות ולעולם לא מוחלף בהתאמה לפי שם: שני «דן
כהן» שההסבה ‎1→2‎ הפרידה בכוונה לשני מזהים נשארים שניים.

מין שסותר בין הרשימה לכרטיס — הכרטיס מנצח (הוא המאגר), והמספר
נרשם ב-`rosterSexConflict`.

### 2 → 3 · `class-identity`

| שלב | פעולה |
|---|---|
| א | כל מפתח ב-`ft.roster` נרשם כ-`Class` |
| ב | כל כיתה שמופיעה אצל תלמיד נרשמת, והתלמיד מקבל `cid` |
| ג | כל מדידה מקבלת `cid` לפי שדה `cls` שלה |
| ד | הכיתה שנטענה לביפ טסט נרשמת |

מדידה **בלי** שדה `cls` מקבלת `cidAmbig:"no-class"` ולא מנוחשת —
אין דרך לדעת לאיזו כיתה היא שייכת, וניחוש כאן שקול לניחוש זהות
תלמיד. הרשומה נשארת שלמה.

כיתה שכבר רשומה לא נדרסת, כי ייתכן שהמורה כבר שינה את שמה — וזה
בדיוק מה שהרישום נועד לשמר.

### 1 → 2 · `student-identity`

| שלב | פעולה |
|---|---|
| א | כל `RosterEntry` בלי `id` מקבל מזהה נגזר |
| ב | כל `Student` ב-`stu.list` בלי `id` מקבל מזהה נגזר |
| ג | כל `Measurement` בלי `sid` משויכת לפי (כיתה, שם) |

בשלב ג יש בדיוק שלוש תוצאות אפשריות:

| מצב | תוצאה |
|---|---|
| התאמה אחת ברשימה | `sid` נכתב, `sidFrom:"migrate/v2"` |
| שתי התאמות או יותר | `sidAmbig:"duplicate-name"` — **לא מנחשים** |
| אין התאמה | `sidAmbig:"no-roster-match"` — **לא מנחשים** |

ניחוש כאן היה מעביר היסטוריה של תלמיד אחד לתלמיד אחר. זה נזק גרוע
בהרבה מרשומה שנשארת מקושרת לפי שם.

**זיהוי גרסה:** מכשיר עם `schema.version` שמור — הערך הזה. מכשיר עם
נתונים אבל בלי סימון — גרסה 1. מכשיר ריק לגמרי — מסומן מיד בגרסה
הנוכחית, כי אין מה להסב. נתונים מגרסה **עתידית** לא נוגעים בהם בכלל.

**עדכון מגרסה 3:** שני תלמידים בעלי אותו שם באותה כיתה מקבלים
מזהים שונים. המזהה הראשון נגזר מ-`כיתה|שם` והבאים מוסיפים סיומת
`#2`, `#3` לפי סדר ההופעה ברשימה השמורה. זה דטרמיניסטי, ובלעדיו שני
תלמידים שונים היו מקבלים זהות אחת — בדיוק הבאג שהמיגרציה באה למנוע.

**עדכון מגרסה 3 (‎3→4‎, `student-class-closure`):** כל תלמיד ב-`stu.list`
בלי `cid` מקבל אותו — דרך הרישום (`findClass`), כך שכיתה ששמה שונה
שומרת על המזהה שלה. `cid` קיים לא מחושב מחדש. תלמיד בלי כיתה מקבל
`cid:null` ו-`cidAmbig:"no-class"` — לא מנחשים. נוגעת ב-`stu.list`
בלבד (ורושמת כיתה חסרה ב-`ft.classes`); `cls` נשאר כהקשר. ראו
`docs/PHASE_8_REPORT.md`.

**הכלל מאז שלב 8:** `cid` הוא הזהות, `cls` הוא ההקשר. הנקודה האחת
שבה תלמיד הופך למזהה כיתה היא `cidOfStudent(stud,store)` ב-`hm-data.js`.

### להוספת גרסה 5

1. להוסיף `{to:5,name:"…",run(store,rep)}` ל-`MIGRATIONS` ב-`hm-data.js`.
2. להעלות את `SCHEMA_VERSION` ל-5.
3. להוסיף בדיקות ל-`tests/unit/migration.test.js`: ספירה לפני/אחרי,

המיגרציות רצות לפי סדר עולה, וכל אחת רק אם `m.to > from`.

## בטיחות אחסון

`LS.get` / `LS.set` ב-`hm-app.js` עוטפים את `safeGet` / `safeSet`
מ-`hm-data.js`. `LS.set` מחזיר `true` או `false` — אף פעם `undefined`.

| קוד | מתי | מה המורה רואה |
|---|---|---|
| `quota` | האחסון מלא | «האחסון במכשיר מלא» + כפתור ייצוא גיבוי |
| `unavailable` | גלישה פרטית, אחסון חסום | «אין הרשאת אחסון» + ייצוא גיבוי |
| `serialize` | נתון פגום או ערך שלא ניתן להמרה | «נמצא נתון פגום» + ייצוא גיבוי |
| `unknown` | כל השאר | «השמירה נכשלה» + ייצוא גיבוי |

האזהרה היא פס קבוע בראש המסך, לא `toast` שנעלם: מורה באמצע מדידה לא
מסתכל על המסך ברגע שהיא מופיעה.

כש-`localStorage` אינו נגיש כלל, האפליקציה עוברת לאחסון בזיכרון כדי
שהשיעור הנוכחי יעבוד — ואומרת בפירוש שדבר לא יישמר.

`window.HM.storage()` מחזיר את מצב האחסון לבדיקות ולאבחון.

```js
    store:"rec", db:"pehub-records", count:12,
    items:[ { …רשומה…, video:{type,name,size,b64} } ],
    omitted:[ {id,name,bytes} ],               // מה שלא נכנס לתקציב
    bytes:…, budget:50331648
  }
}
```

מוצפן: אותו אובייקט בתוך `{kind:"backup-encrypted", alg:"AES-GCM",
kdf:"PBKDF2-SHA256", iter:310000, salt, iv, ct}`. המעטפת גלויה
בכוונה; שמות התלמידים, שם בית הספר ואפילו שמות המפתחות — בפנים.

### תקציב מדיה

סרטון הוא מגה-בייטים. התקציב הוא 48MB, והבחירה היא מהחדש לישן. מה
שלא נכנס **מדווח בשמו ובגודלו בתוך הקובץ**, מוצג למורה בייצוא ושוב
בתצוגה המקדימה של השחזור. **רשומת השיא עצמה תמיד נכנסת** גם כשהסרטון
שלה לא — שיא בלי וידאו עדיף על שיא שנעלם.

### שחזור

1. **ולידציה לפני שנוגעים במשהו** — `validateBackup`. קובץ שנחתך,
   קובץ של אפליקציה אחרת וקובץ מגרסה חדשה יותר נדחים בהודעה מפורשת.
2. **תצוגה מקדימה** — `planRestore` מראה מה ייכנס, מה יידרס ומה ייעלם.
3. **גיבוי ביטחון** בלחיצה, באותו חלון.
4. **`localStorage` מוחלף ולא ממוזג** — מיזוג של שתי היסטוריות מדידה
   היה יוצר כפילויות שקטות.
5. **`IndexedDB` מתווסף ולא מוחק** — שיא שקיים רק במכשיר נשאר.
6. **ההסבה רצה על מה ששוחזר**, כדי שקובץ ישן לא ישאיר סכמה ישנה.

### שני מסלולי ייצוא

| מסלול | כולל סרטונים | מתי |
|---|---|---|
| «גיבוי» בהגדרות | כן | הגיבוי הרגיל |
| `bkExport()` — «ייצא גיבוי עכשיו» | לא | הצלה: כשהאחסון כבר נכשל, או גיבוי ביטחון לפני שחזור. סינכרוני ומיידי. |

## מדידות שממתינות להכרעה

מדידה שההסבה לא הצליחה לשייך בוודאות מסומנת ב-`sidAmbig` ונשארת
נגישה לפי שם. המורה מכריע בה ידנית מכרטיס «מדידות שממתינות להכרעה»
במסך בחירת הכיתה — כרטיס שמופיע **רק** כשיש בכיתה מה להכריע.

הכלל: **המערכת לעולם לא מנחשת.** לא לפי השם הראשון שמתאים, לא לפי
מיקום במערך, לא לפי סדר אלפביתי ולא לפי דמיון מחרוזות. היא מסדרת
את המועמדים — תלמידי אותה כיתה, ובראשם מי ששמו תואם — והמורה בוחר.

אחרי בחירה: `sid` נכתב, `sidFrom` נעשה `"manual"`, והסימון יורד.
הסימון יורד **רק** אחרי שיוך שהצליח. רשומה שלא הוכרעה נשארת שלמה
ונגישה בדיוק כמו קודם.

## מה עדיין לא פתור

ביושר:

- **אין מגבלת גודל על `ft.results`.** היא גדלה לנצח עד שהמכסה
  נגמרת. יש ניקוי ידני בהגדרות, אבל אין אזהרה מקדימה. זה הפער
  הפתוח הגדול ביותר במודל הנתונים.
- **חמש נקודות חישוב ניקוד כפול.** מתועדות; לא מסוכנות, מכוערות.

שלושה פערים שהופיעו כאן בעבר **נסגרו**, ומתועדים כדי שלא ייפתחו
שוב: ממשק לשינוי שם כיתה (יש, בהגדרות), סינון כיתה לפי מחרוזת
(הכול עובר דרך `cid`), ו«שתי הרשימות» — ראו למטה.

## שתי הרשימות — איך הן הפכו לאחת

עד סכמה 5 היו כאן **שני מאגרים לאותם ילדים**: `stu.list` (כרטיס
תלמיד מלא) ו-`ft.roster` (שורה ברשימת כיתה, עם שם ומין משלה). הם
לא אוחדו בשלב 3 במכוון — האיחוד נוגע בכל אחד ממסלולי היצירה, וזה
לא היה «שינוי קטן ובטוח».

**מה שאילץ את האיחוד בסוף:** המין ישב בשניהם, והוא קובע נורמה.
כפתור «בן/בת» ברשימת הכיתה כתב לצד אחד, כרטיס התלמיד לצד השני,
ואף אחד מהם לא עדכן את השני. כלומר אותו תלמיד יכול היה לקבל ציון
לפי נורמת בנים במסך אחד ולפי נורמת בנות בשני — בלי שום סימן שיש
כאן סתירה. שני מאגרים שמחזיקים את אותו שדה הם שתי תשובות לאותה
שאלה, ואחת מהן שקרית ברגע שמישהו עורך צד אחד.

**המצב מאז ‎4→5‎:**

| | `stu.list` | `ft.roster[cid]` |
|---|---|---|
| מה | כל מה שידוע על התלמיד | מי בכיתה, ובאיזה סדר |
| שדות | שם, מין, גיל, גובה, משקל, מבחני ריצה, ציונים | מזהים בלבד |
| כיתה | `cid` (ו-`cls` כהקשר) | המפתח במפה |
| נוצר ב | «התלמידים שלי», ייבוא CSV, הוספה לרשימת כיתה, לוח הביפ | — |

**הוספה לרשימת כיתה היא יצירת תלמיד.** «+ תלמיד», הדבקת שמות
וייבוא CSV — כולם עוברים דרך `setRosterOf`, שיוצר את הכרטיס אם
הוא חסר. אין יותר תלמיד שקיים ברשימה ולא ב«התלמידים שלי», ולכן
גם אין יותר תיבת סימון «להוסיף גם ל«התלמידים שלי»» בייבוא.

**מחיקה היא גם מחיקה אחת.** מחיקת כרטיס מסירה את המזהה מכל
רשימות הכיתה (`removeFromRosters`) — אחרת היה נשאר מזהה בלי
תלמיד. המדידות נשארות, מקושרות ל-`sid`, ויחזרו אם יוסיפו אותו שוב.

**מה ההסבה עושה:** כל שורה ברשימה הופכת למזהה; תלמיד שהיה רק
ברשימה מקבל כרטיס; המפתח עובר מתווית (`"ט3"`) ל-`cid`
(`"c:ט:3"`). מפתח שאי אפשר לפתור לזהות אחת (שתי כיתות באותו שם)
**נשאר כפי שהוא** — לא מנחשים — והקריאה המגוננת ממשיכה לשרת אותו.
מין שסותר בין הרשימה לכרטיס: הכרטיס מנצח, והמספר נרשם בדוח
ההסבה (`rosterSexConflict`) כדי שזה לא יקרה בשקט.
